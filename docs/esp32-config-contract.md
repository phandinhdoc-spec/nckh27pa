# Canonical Android ↔ ESP32 local configuration contract

**Status:** FROZEN for implementation — reviewed by Hermes; incompatible changes require a contract revision  
**Contract revision:** 1  
**Local transport API:** `1`  
**ESP32 detection config schema:** `1`

This file is the sole authority for the local Android ↔ ESP32 configuration path. It does not change BLE protocol v1 in `docs/interface-contract.md`, does not use the remote Node `/api/v1`, and does not claim acceptance on unconfirmed hardware. The first implementation must be proven with the host simulator and a reference Arduino adapter; board, pins, IMU, BMP390 wiring, Wi-Fi behavior, and flash behavior remain hardware-unverified.

All thresholds and defaults below are initial experimental values. They are neither medical standards nor evidence of diagnostic accuracy. BMP390 pressure and estimated height never determine a fall by themselves.

## 1. Scope, authority, and user-visible truth

There are two independent configuration domains:

- `profileTarget: "PHONE"`: Android's local phone detector configuration. Android is authoritative.
- `profileTarget: "ESP32"`: a saved Android-side profile intended for an ESP32. The device's read-back is authoritative for what the ESP32 is actually running.

No profile is silently copied or translated between targets. Saving an Android profile is not applying it to the device. The UI and repository must distinguish:

1. **DRAFT** — editable values not yet durably saved.
2. **SAVED** — an Android snapshot was durably saved, but it is not thereby active on any ESP32.
3. **DEVICE_CONFIRMED** — a completed apply response was followed by a read-back matching the exact profile ID, profile revision, config hash, and config values.

`DEVICE_CONFIRMED` describes one immutable confirmation snapshot. Editing or saving that profile later increments its `profileRevision` and makes the newer revision merely `SAVED`; the old confirmation may remain in history but must not be presented as confirmation of the edited revision. Disconnecting does not erase the snapshot, but current device state becomes unverified until read-back.

Fall/SOS authority remains unchanged: configuration networking must never cancel, restart, delay, acknowledge, or synthesize an SOS/countdown. The device remains responsible for its active local alert state.

## 2. Versions and identifiers

| Name | Type | Rule |
|---|---|---|
| `apiVersion` | integer | Local HTTP transport/envelope version; exactly `1` here. |
| `schemaVersion` | integer | ESP32 detection config schema; exactly `1` here. |
| `profileTarget` | string enum | `PHONE` or `ESP32`; this HTTP path accepts only `ESP32`. |
| `profileId` | string | Stable RFC 4122 UUID generated by Android, lowercase canonical text recommended; never changes on Save. |
| `profileNumber` | integer | Positive, monotonically allocated per target; never reused. Display name is exactly `Bảng N`. Not sent to the device because it has no runtime meaning. |
| `profileRevision` | integer | Positive 64-bit value. Starts at `1`; every successful Save of that profile increments it by one, even when values are unchanged. Save As creates a new ID at revision `1`. |
| `configRevision` | integer | Positive, device-owned, monotonically increasing 64-bit applied revision. It increases once for each newly persisted `configHash`, survives reboot, and is never supplied as the next value by Android. |
| `configHash` | string | 64 lowercase hexadecimal SHA-256 characters over the canonical apply document defined in §7. |
| `requestId` | string | RFC 4122 UUID generated by Android for one logical apply/reset operation. A retry reuses it. |
| `deviceId` | string | Stable device identifier; existing `FALLSAFE-` naming remains valid. |
| timestamps ending `Ms` | integer or documented null | Unix epoch milliseconds. Durations/ordering in engines use monotonic clocks. A device with unsynchronized wall time returns null rather than fake epoch time. |

### 2.1 Android snapshot migration

Existing `fallsafe_detection_profiles_v1_<userId>` data is the phone profile snapshot v1 and must not be dropped, reset, renumbered, or interpreted as ESP32 configuration. The Android implementation migrates it atomically to snapshot schema v2 as follows:

- preserve every existing profile's `id`, `profileNumber`, `displayName`, timestamps, active flag, seven existing motion values, and `lastAssignedProfileNumber`;
- set `profileTarget = PHONE` and `profileRevision = 1` on each migrated profile;
- add the phone pressure fields from §4 at their defaults, preserving detector behavior because the toggle defaults off;
- create an independent empty ESP32 profile collection and ESP32 high-water mark; its first explicit/default creation is `Bảng 1`, revision `1`, and is inactive/unapplied;
- commit the complete v2 snapshot atomically; if writing fails, retain/read v1 and report storage failure rather than deleting it.

Snapshot v2 keeps separate per-target numbering high-water marks. Exactly one PHONE profile remains active. ESP32 profiles use no Android runtime `isActive` flag: “selected”, “saved”, and “device-confirmed” are separate facts.

## 3. ESP32 detection configuration schema v1

The configuration is a full replacement object. Every field is required. JSON numbers must be finite; NaN and infinity are invalid JSON and invalid configuration. Integer means an unquoted base-10 JSON integer. Unknown, duplicate, missing, wrong-type, or out-of-range fields reject the entire request; firmware must never ignore them or retain a hidden old field.

The detector preserves the transparent motion sequence: **impact at or above the impact threshold, then qualifying post-impact stillness inside the window**. Pressure can only annotate/corroborate that already-complete motion sequence. Pressure never starts `SUSPECTED`, never confirms a fall alone, never vetoes valid motion evidence, and never blocks SOS.

| Field | Type | Default | Inclusive min…max | Runtime use |
|---|---:|---:|---:|---|
| `impactAccelerationMs2` | number, max 3 decimals | `25.000` | `1.000…100.000` | Impact when acceleration magnitude is at least this value. |
| `stillnessTargetAccelerationMs2` | number, max 3 decimals | `9.810` | `0.000…20.000` | Center of post-impact stillness band. |
| `stillnessToleranceMs2` | number, max 3 decimals | `1.000` | `0.100…10.000` | Absolute deviation allowed around the stillness target. |
| `postImpactWindowMs` | integer | `3000` | `500…10000` | Maximum monotonic time after impact in which stillness may complete. |
| `postImpactStillnessDurationMs` | integer | `1000` | `100…10000` | Required continuous qualifying stillness duration. |
| `minimumStillnessSamples` | integer | `6` | `2…100` | Required qualifying samples in that duration. |
| `maximumSampleGapMs` | integer | `250` | `10…2000` | A larger/non-monotonic IMU gap clears in-progress evidence. |
| `pressureEvidenceEnabled` | boolean | `false` | — | Enables supplementary pressure corroboration only. |
| `pressureMinimumRisePa` | number, max 2 decimals | `12.00` | `1.00…200.00` | Minimum positive filtered pressure rise across the evidence window to mark descent corroboration. |
| `pressureWindowMs` | integer | `3000` | `500…10000` | Window ending when the motion sequence confirms; see §5. |
| `pressureMinimumSamples` | integer | `5` | `2…100` | Minimum fresh valid pressure samples in the evidence window. |
| `pressureFilterAlpha` | number, max 3 decimals | `0.200` | `0.010…1.000` | EMA coefficient for pressure telemetry/evidence. |
| `pressureStaleAfterMs` | integer | `1000` | `100…5000` | Age after which last pressure is stale and pressure-derived values become null. |

Cross-field rules:

- `postImpactStillnessDurationMs <= postImpactWindowMs`.
- `pressureStaleAfterMs <= pressureWindowMs`.
- If `pressureEvidenceEnabled` is true and the capability says BMP390/barometer is absent, unavailable, or unsupported, apply fails with `SENSOR_UNAVAILABLE`; firmware must not silently turn the toggle off.
- A config is accepted only if all schema-v1 fields are listed as supported by capabilities. Otherwise Android reports `INCOMPATIBLE_SCHEMA` and does not apply.

Example default ESP32 config object:

```json
{
  "impactAccelerationMs2": 25.000,
  "stillnessTargetAccelerationMs2": 9.810,
  "stillnessToleranceMs2": 1.000,

  "postImpactStillnessDurationMs": 1000,
```

## 4. Minimal phone-barometer extension

Phone and ESP32 schemas remain separate. Snapshot schema v2 adds exactly these fields to the existing seven-field `FallDetectionConfig`:

| Field | Type | Default | Inclusive range | Meaning |
|---|---:|---:|---:|---|
| `phonePressureEvidenceEnabled` | boolean | `false` | — | Opt-in supplementary phone pressure evidence. |
| `phonePressureMinimumRisePa` | number, max 2 decimals | `12.00` | `1.00…200.00` | Positive rise across the existing five-second phone pressure history required for corroboration. |

When off, unavailable, denied by capability, invalid, or stale, the phone detector behaves exactly as before: its seven motion fields alone drive impact plus stillness. When on and fresh pressure exists, `latestPressurePa - oldestPressurePa` in the bounded existing five-second history is compared to `phonePressureMinimumRisePa` only after the motion sequence confirms. A passing value may set `pressureCorroborated=true` in observation/trial evidence or raise a non-medical rule score, but cannot itself trigger a fall, cannot remove the required impact/stillness sequence, and a failing/missing value cannot suppress that sequence.

The Android UI exposes the toggle and threshold only when `TYPE_PRESSURE` capability is present. If absent, it shows pressure as unavailable, keeps the stored value, forces runtime use to disabled, and does not rewrite the profile merely because this phone lacks the sensor. The value is in Pa; Android's existing hPa sensor input must continue conversion by multiplying by 100.

## 5. BMP390 pressure and reference semantics

### 5.1 Values and signs

- `pressureCurrentPa`: latest fresh EMA-filtered pressure in Pa.
- `pressureReferencePa`: explicit/bootstrap reference in Pa.
- `pressureDeltaPa = pressureCurrentPa - pressureReferencePa`; positive normally means descent.
- `altitudeDeltaM = 44330 * (1 - (pressureCurrentPa / pressureReferencePa)^(1 / 5.255))`; positive estimates ascent and negative estimates descent.
- `pressureWindowDeltaPa`: latest minus earliest filtered sample in the configured evidence window; positive normally means descent.

`altitudeDeltaM` is an environmental estimate, not measured fall height. All derived fields are null unless both inputs are valid and fresh. Missing, error, calibrating, or stale data is represented by a status plus null, never by zero.

### 5.2 Sampling, filtering, window, and stale rules

For every valid finite BMP390 sample greater than zero, in monotonic timestamp order:

1. Initialize EMA to the first sample; afterward compute `filtered = alpha * raw + (1 - alpha) * previousFiltered`, using `pressureFilterAlpha`.
2. Store at most the samples in the last `pressureWindowMs` and a hard maximum of 128 filtered samples; discard oldest first.
3. Pressure corroboration at motion confirmation is true only when enabled, status is `OK`, at least `pressureMinimumSamples` filtered samples exist in the window ending at confirmation, newest age is at most `pressureStaleAfterMs`, and `newest - oldest >= pressureMinimumRisePa`.
4. If the newest age exceeds `pressureStaleAfterMs`, status is `STALE`; `pressureCurrentPa`, `pressureDeltaPa`, `pressureWindowDeltaPa`, and `altitudeDeltaM` are null until a new valid sample arrives. The persisted reference remains intact.
5. Driver read failure sets `ERROR`; physical absence sets `UNAVAILABLE`; collection before a reference exists sets `CALIBRATING`. Invalid/out-of-order samples are not converted to zeros or inserted.

### 5.3 Reference bootstrap/reset and lock

At boot, when a barometer is present, firmware performs one bootstrap attempt: collect `pressureMinimumSamples` valid raw samples within `pressureWindowMs`. If their maximum minus minimum is at most the fixed initial experimental stability limit `10.00 Pa`, set the reference to their arithmetic mean and persist it. If not, remain `CALIBRATING` and permit monitoring without pressure evidence; do not fabricate a reference. A later reference change requires the explicit reset endpoint in §6.

A reset performs the same collection/stability rule and is atomic: the old reference remains active until a new stable reference is persisted. During `SUSPECTED`, `VERIFYING`, or `LOCAL_ALERTING`, both config apply and reference reset are rejected with `BUSY_ALERT_ACTIVE`. The reference is locked until the state leaves those three states; normal pressure sampling, EMA updates, and the event window continue against that unchanged reference. There is no periodic or silent reference reset.

## 6. Local HTTP transport

**Explicit origin:** `http://192.168.4.1`  
**Base path:** `/api/v1`  
**Media type:** request and response `application/json; charset=utf-8` (requests may send `application/json`; no other request media type).  
**Request body limit:** 8192 UTF-8 bytes, checked before JSON parsing.  
**Response body limit for Android:** 32768 UTF-8 bytes; larger responses are protocol errors.  
**Redirects:** forbidden. Android must not follow them.  
**Compression:** not used in v1.

Android timeouts: connect `3000 ms`; read `5000 ms` for GET/status; call `10000 ms` for apply and reference reset. One automatic transport retry is allowed only with the same `requestId`; after that reconcile by GET. These are local HTTP timeouts, not detector/countdown timers.

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/api/v1/device/capabilities` | Firmware/schema/transport/sensor support and exact editable fields/ranges. |
| `GET` | `/api/v1/device/status` | Device state, sensor status, and applied identity. |
| `GET` | `/api/v1/device/config` | Canonical current applied config/read-back. |
| `PUT` | `/api/v1/device/config` | Validate, atomically persist, and apply a full config. |
| `GET` | `/api/v1/sensors/latest` | Latest sensor/feature snapshot; keeps the existing planned path. |
| `POST` | `/api/v1/device/reference-pressure/reset` | Explicitly collect and atomically replace pressure reference. |

Every success uses `{"success":true,"data":...,"timestampMs":...}`. `timestampMs` is nullable when device wall time is unsynchronized. Every failure uses §9's envelope.

Successful GET, PUT, and POST operations return `200 OK`. V1 does not use `201`, `202`, or `204`: apply/reset are synchronous and a body is always returned. Before the first valid config exists, GET `/api/v1/device/config` returns `404 CONFIG_NOT_INITIALIZED`; status still returns `200` with `applied:null`. Unsupported paths/methods and all other failure statuses are defined in §9.

## 7. Deterministic hash and apply handshake

### 7.1 Canonicalization shared by Android and C++

The hash input is UTF-8 with no BOM and no trailing newline. It is exactly one compact JSON object with keys in the order below. No spaces are permitted. Strings are ASCII UUID/enum tokens and JSON-escaped by the normal JSON rules. Booleans are lowercase. Integers use shortest base-10 form with no leading zero. Decimal fields use fixed digits after the decimal point, including trailing zeros: three digits for acceleration and alpha; two for pressure threshold.

Ordered hash members:

1. `schemaVersion`
2. `profileTarget`
3. `profileId`
4. `profileRevision`
5. `config`, whose keys occur in the exact §3 table order

`apiVersion`, `requestId`, `expectedConfigRevision`, `configRevision`, and `configHash` are excluded. Compute SHA-256 over those bytes and encode lowercase hexadecimal. Parsing must first reject values with more precision than allowed; implementations must not round differently.

Canonical bytes corresponding to §6.3 (shown as JSON and also mechanically valid):

```json
{"schemaVersion":1,"profileTarget":"ESP32","profileId":"4ce38b32-baa5-4f3f-99be-8a920bd2d17d","profileRevision":3,"config":{"impactAccelerationMs2":25.000,"stillnessTargetAccelerationMs2":9.810,"stillnessToleranceMs2":1.000,"postImpactWindowMs":3000,"postImpactStillnessDurationMs":1000,"minimumStillnessSamples":6,"maximumSampleGapMs":250,"pressureEvidenceEnabled":false,"pressureMinimumRisePa":12.00,"pressureWindowMs":3000,"pressureMinimumSamples":5,"pressureFilterAlpha":0.200,"pressureStaleAfterMs":1000}}
```

The expected SHA-256 is `88dcc136a42afb992df14823614f9f9f4459e4093ade82be7e5624dd5a4b11fe`.

### 7.2 Atomic apply and reconciliation

Firmware executes one transaction/critical operation: parse strictly → validate schema/capability/cross-fields/hash/revision/state → persist a checksummed complete record → make it the runtime config → return `COMPLETED`. Runtime evidence is cleared at the boundary so samples from different configs are never mixed. If any stage fails, runtime and durable prior config remain unchanged. A failed or torn flash write must recover the last valid record on restart.

For a new hash, increment and persist `configRevision` exactly once. If the incoming hash equals the currently applied hash, return `COMPLETED`, the current revision, and `changed:false`; do not write flash or reset detector evidence.

Android may display **APPLIED** only after:

1. the PUT returns a valid `COMPLETED` response with the same `requestId`; and
2. a subsequent GET `/device/config` exactly matches `profileId`, `profileRevision`, `configHash`, every typed config value after canonical precision normalization, and the response's `configRevision`.

A timeout, disconnect, malformed response, or lost response after the request may mean the device committed. Android must show `UNKNOWN_CONFIRMATION` / “CHƯA XÁC NHẬN”, not failure and not APPLIED. On reconnect it GETs config and reconciles: exact match becomes APPLIED; a mismatch becomes READY/SAVED and may be retried as a new user action after refreshing `expectedConfigRevision`.

Firmware keeps at least the latest 16 terminal request results for the current boot, keyed by `requestId` and canonical semantic request hash. The request ID/hash/result that actually committed the current config is also stored inside that same atomic config record, not in a second write. Repeating a retained ID with an identical request returns the original terminal response without reapplying. Reusing a retained ID with different semantics returns `409 REQUEST_ID_REUSED`. Different request IDs with the same current `configHash` are successful unchanged operations as above and may be cached in RAM, but cause no flash write. After reboot, an ambiguous client reconciles by GET rather than relying on replay cache; the committing request remains replayable from the config record.

## 8. Profiles and trial linkage on Android

ESP32 profiles are persistent, multiple, and system-numbered. `profileId` is stable; `profileNumber` and `Bảng N` never change. Allocation is `max(highWaterMark, largestExistingNumber) + 1`; deletion never lowers the mark. Save replaces one profile and increments its revision only after durable success. Save As creates a new inactive/unapplied profile and leaves its source unchanged. Selection does not apply. Applying does not make it a PHONE active profile.

Deleting an ESP32 profile deletes only the Android saved profile. It never sends a delete/reset to the ESP32 and never claims the device stopped using the already-applied config. A retained confirmation snapshot may refer to a deleted local profile and must be labeled accordingly. Device confirmation linkage stores `deviceId`, `profileId`, `profileRevision`, `configRevision`, `configHash`, exact confirmed config, and confirmation time; later profile edits do not mutate it.

```json
{
  "source": "ESP32",
  "deviceId": "FALLSAFE-01A2",
  "profileId": "4ce38b32-baa5-4f3f-99be-8a920bd2d17d",
  "profileRevision": 3,
  "appliedConfigRevision": 8,
  "appliedConfigHash": "88dcc136a42afb992df14823614f9f9f4459e4093ade82be7e5624dd5a4b11fe",
```

`source` is `PHONE` or `ESP32`. A PHONE record uses its phone profile identity/revision and null for both applied-device fields; it does not pretend to be device-confirmed.

## 9. Errors, HTTP codes, and UI state

Error envelope:

```json
{
  "success": false,
  "error": {
    "code": "BUSY_ALERT_ACTIVE",
    "message": "Configuration is locked while a local alert is active.",
    "field": null,
    "retryable": true,
    "details": {"localAlertState": "VERIFYING"}
  },
  "requestId": "b94aa842-29bb-44b2-9908-2505b10b49aa",
  "timestampMs": 1789363200200
}
```

`message` is diagnostic, not a programmatic key. `field` is the exact offending JSON path or null. `details` is an object and may be empty. `requestId` is echoed when it was parsed, otherwise null.

| HTTP | Error code | Meaning / retry |
|---:|---|---|
| `400` | `MALFORMED_JSON` | Invalid JSON, duplicate key, or wrong primitive/container shape; fix request. |
| `400` | `INVALID_REQUEST_ID` | Missing/non-UUID request ID; new valid ID required. |
| `404` | `NOT_FOUND` | Unknown local endpoint. |
| `404` | `CONFIG_NOT_INITIALIZED` | No valid applied config exists yet; apply with expected revision `0`. |
| `405` | `METHOD_NOT_ALLOWED` | Known endpoint, wrong method. |
| `409` | `BUSY_ALERT_ACTIVE` | `SUSPECTED`, `VERIFYING`, or `LOCAL_ALERTING`; no queue/defer; retry only after safe state. |
| `409` | `REVISION_CONFLICT` | `expectedConfigRevision` stale; GET and require explicit reapply. |
| `409` | `REQUEST_ID_REUSED` | Same request ID, different payload; generate a new ID only for a new logical operation. |
| `413` | `BODY_TOO_LARGE` | Request exceeds 8192 bytes. |
| `415` | `UNSUPPORTED_MEDIA_TYPE` | Not JSON. |
| `422` | `INCOMPATIBLE_SCHEMA` | API/schema/target unsupported. |
| `422` | `UNSUPPORTED_FIELD` | Unknown field or capability does not support it. |
| `422` | `MISSING_FIELD` | Required field absent. |
| `422` | `VALIDATION_ERROR` | Type, precision, bound, or cross-field rule failed. |
| `422` | `HASH_MISMATCH` | Supplied hash differs from canonical calculation. |
| `422` | `SENSOR_UNAVAILABLE` | Enabled feature requires unavailable/failed sensor, or reset cannot use BMP390. |
| `500` | `STORAGE_ERROR` | Atomic persistence failed; previous config/reference retained. Retryable after status check. |
| `500` | `INTERNAL_ERROR` | Bounded generic failure; no partial apply. |
| `503` | `SENSOR_UNAVAILABLE` | Latest required sensor data cannot be served. |
| `504` | `REFERENCE_UNSTABLE` | Reset could not collect stable samples in its bounded window; old reference retained. |

UI state is a view of transport/handshake, not the firmware alert state:

| UI state | Enter when |
|---|---|
| `DISCONNECTED` | No reachable local origin/network. |
| `READING` | Capabilities/status/config read in progress. |
| `READY` | Compatible read completed; draft/saved profile may be applied. |
| `APPLYING` | PUT or mandatory read-back is in progress. |
| `APPLIED` | Completed response plus exact read-back match. |
| `REJECTED` | Terminal device rejection not represented more specifically. |
| `UNKNOWN_CONFIRMATION` | Apply outcome ambiguous or confirmation read-back unavailable. Vietnamese label: “CHƯA XÁC NHẬN”. |
| `BUSY_ALERT_ACTIVE` | Error code of same name; SOS/countdown UI remains authoritative and unaffected. |
| `INCOMPATIBLE_SCHEMA` | API/schema/required field set mismatch. |
| `VALIDATION_ERROR` | Any request field/precision/bound/cross-field error; highlight `field`. |
| `SENSOR_UNAVAILABLE` | Required sensor absent/error; pressure controls disabled when appropriate. |
| `STORAGE_ERROR` | Device or Android durable write failed; do not claim save/apply. |
| `REVISION_CONFLICT` | Device changed since read; refresh before explicit reapply. |
| `REFERENCE_UNSTABLE` | Reference reset failed; old reference remains. |

HTTP status alone never maps to APPLIED. Unknown/unrecognized error codes map to `REJECTED` for terminal 4xx, `UNKNOWN_CONFIRMATION` for ambiguous transport/5xx after an apply may have been sent, and retain the raw safe code only in diagnostics (not raw payload/secrets).

## 10. Busy and safety policy

The deterministic v1 policy is **reject, never defer**. Apply and reference reset during `SUSPECTED`, `VERIFYING`, or `LOCAL_ALERTING` return `409 BUSY_ALERT_ACTIVE` without validation-side mutation, persistence, queueing, or later automatic application. Reads remain available. `MONITORING` and `DEGRADED` may accept configuration if all required capabilities for that config are healthy; pressure-enabled apply in barometer degradation is rejected as `SENSOR_UNAVAILABLE`.

Configuration calls do not alter the countdown deadline, buzzer, active event ID, event acknowledgement, SOS button path, or local transition. SOS always has priority over config processing; if state becomes active before commit, abort and retain the prior config.

## 11. Security and local deployment constraints

- The endpoint exists only in explicit technical AP mode at `192.168.4.1`; it is not bound/routed to an Internet-facing interface and is disabled outside that mode.
- Android cleartext permission must be scoped to this local origin/network configuration, never enabled globally for arbitrary hosts.
- Do not embed AP passwords, provisioning tokens, user credentials, or reusable secrets in the repository, APK constants, firmware source, fixtures, or logs.
- Lab AP authentication/provisioning and the physical action that enables technical mode are deployment-specific until board/hardware choices are confirmed. This contract does not weaken that requirement or invent credentials.
- Reject non-local Host/origin use, redirects, and DNS substitution. Local HTTP provides no confidentiality by itself; operate only on the isolated technical AP.
- Remote Node backend and cloud services are not intermediaries for this path.

## 12. Acceptance and test matrix

|---|---|---|
| C01 | Happy apply | Capability/read → PUT COMPLETED → exact GET; UI APPLIED; one config revision increment. |
